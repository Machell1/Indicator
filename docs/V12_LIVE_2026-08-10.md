## NEW FINDING — the two label sets overprint each other

The edge profile's key-row labels collide with the in-chart developing
label column. Read literally off the frame:

```
VAH 4480.3480.3        <- "VAH 4480.3" over "dVAH 4480.3"
POC 4457.5157.5        <- "POC 4457.5" over "dPOC 4457.5"
VAL 4454.054.0         <- "VAL 4454.0" over "dVAL 4454.0"
```

Arithmetic: edge labels sit at `px(-(170 + 140 + 4))` = **314px** from
the pane's right edge, i.e. x≈931. The in-chart column sits at bar
`i + 4`, which on this frame is x≈890-960. They land on top of each
other.

**This is the compounding that handoff open question 3 flagged.** The
"both stay ON" decision is defensible on the merits — the two views do
serve different reads — but this is its direct cost, and it is now on the
chart. Note the values are *identical*, not merely adjacent: the edge
profile IS the developing session's profile, so this is pure duplication
rendered twice in the same place.

**It cannot be fixed with a static offset.** The two label sets are
anchored in different spaces — one px-from-right, one bar-index — so
their separation changes with every scroll and zoom. Any constant that
works on this frame breaks on the next pan.

### Recommended fix: suppress the IN-CHART dev key labels while `edgeProfile` is ON

Not the edge ones. The direction matters and it is not arbitrary:

**The edge labels are the anchor-immune pair.** During the daily-break
AUTO flip the in-chart column is precisely what mis-places — that is the
entire insurance argument for this family. Dropping the edge labels to
resolve the collision would leave the broken hour with rows but no
readable VAH/POC/VAL, defeating the purpose of building it. Dropping the
in-chart ones costs nothing, because the edge labels carry the same three
values and keep carrying them when the other set is wrong.

Keep `dev` rows in-chart as decided — this is about the three key-row
labels only.

## MINOR — a vacuous assertion in sim part 22

```js
check(/[*]?$/.test(ch.text) && /(VAH|POC|VAL) /.test(ch.text), ...)
```

`/[*]?$/` matches **every** string — an optional character at
end-of-string is trivially satisfiable. The `(VAH|POC|VAL)` half is real;
the `*`-convention half tests nothing. Suggest `/\*$/` guarded on
`barMin !== 1`, or drop the clause rather than leave a check that reads
like coverage it does not provide. Everything else in part 22 is genuine
— the `JSON.stringify` container comparison under a forced `duTime`
change and the additive key-set check are exactly the right instruments.
